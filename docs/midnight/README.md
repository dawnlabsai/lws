# Midnight in OWS — command-by-command reference

This folder documents how the `ows` CLI works **for the Midnight chain**, one command
at a time. Each file explains the exact code path, the reasoning behind it, how it
differs from the other chains OWS supports, and how it was validated end-to-end on the
live `midnight:preview` testnet.

Midnight is unlike every other chain OWS integrates: a single wallet holds value in
**three independent domains** (unshielded, shielded, and dust), transactions are
zero-knowledge-proven artifacts rather than plain signed bytes, and the wallet — not the
dApp — is what balances and pays fees. Those differences ripple through almost every
command, so this reference exists alongside the generic `docs/` so a reader never has to
reverse-engineer "what does this command actually do on Midnight?".

## The four milestones

The Midnight integration landed as four stacked pull requests. Each command below notes
which milestone introduced its Midnight behavior.

| Milestone | PR | What it added | Commands touched |
|-----------|----|----|----|
| **Midnight 0** | #13 | Address derivation via multi-key derivation params | `mnemonic derive`, `wallet create/import/list` |
| **Midnight 1** | #14 | `fund balance`: unshielded + shielded + dust | `fund balance` |
| **Midnight 2** | #15 | Transaction signing: DApp-connector methods, sign → prove → seal → submit | `sign tx`, `sign send-tx`, `sign message` |
| **Midnight 3** | #18 | Effect-aware second policy pass at the connector seam | `sign tx`, `policy create`, `key create` |

## Core concepts shared across the commands

These ideas recur in every command doc; they are collected here once.

### The three value domains

A Midnight account is not one balance — it is three, each with its own keys, its own
address, its own ledger sync, and its own role in a transaction:

- **Unshielded (Night)** — the public UTXO ledger. Balances and transfers are visible
  on-chain, like a transparent account. Backed by a BIP-340 (Schnorr, secp256k1) key.
- **Shielded (Zswap)** — the private, zero-knowledge coin ledger. Ownership is proven,
  not revealed. Backed by a Zswap secret-key bundle (a coin secret key + an encryption
  secret key) derived from a dedicated seed.
- **Dust** — Midnight's fee currency, generated by *registering* NIGHT UTXOs. Fees are
  **always paid in dust**, never in the token being transferred. Backed by its own dust
  secret key.

Every command that shows balances (`fund balance`) or moves value (`sign tx`,
`sign send-tx`) has to reckon with all three.

### One mnemonic, three role seeds, one packed key

Midnight derives three 32-byte seeds under one BIP-44 tree
(`m/44'/2400'/0'/{role}/{index}`, roles `0`=unshielded, `2`=dust, `3`=shielded). To ride
OWS's single-signing-key channel, the three seeds are packed into one opaque blob —
a 4-byte magic prefix `MNK1` followed by the three concatenated seeds
(`MAGIC || unshielded || shielded || dust`). The magic prefix means a **raw-imported
private key** (which carries no packed roles) is never mistakenly split into role seeds;
it simply yields no Midnight capability, so shielded/dust degrade to "unavailable" rather
than erroring. See [mnemonic-derive.md](./mnemonic-derive.md) and [wallet.md](./wallet.md).

### Network identity is a verbatim CAIP-2 reference

A Midnight network is identified by the reference after `midnight:` — `mainnet`,
`preview`, `preprod`, or any ad-hoc feature testnet like `feature-x`. The reference is
kept **verbatim** (lowercased) and never mapped to a fixed set, so an unregistered network
is never silently cast to mainnet. Only `mainnet` gets an empty Bech32m HRP suffix; every
other network carries `_{reference}` in the HRP of all four address kinds
(`mn_addr_preview…`, `mn_shield-addr_preview…`, `mn_dust_preview…`,
`mn_shield-esk_preview…`). The reference also becomes the transaction's `network_id`.

### The seed-free crypto provider

`ows-midnight` (the crate that does all the network orchestration — balance sync,
connector balancing, dapp-connector methods) holds **no raw key material**. All key
derivation and key-bearing work is owned by `ows-signer` behind a per-account capability
object, `MidnightCryptoProvider`:

- `MidnightSigner` is **stateless** — network identity, HRPs, address derivation,
  encode/decode of the packed key. It is the factory: `signer.crypto_provider(&credential)`
  decodes the packed blob **once**.
- `MidnightCryptoProvider` is **stateful, per-account** — it owns the decoded seeds and
  the derived Zswap/dust keys, and exposes only *public* values (verifying key, dust
  public key, addresses) plus *keyful-but-opaque* operations (fold a ledger event into
  wallet state; authorize a shielded input or dust fee). The typed secret keys never
  leave the provider.

`ows-lib` sits at the boundary: it holds the credential, builds one
`MidnightCryptoProvider`, and hands only `&provider` into `ows-midnight`. This is why
`fund balance` and `sign tx` both route through `ows-lib` first — it is the only layer
that ever touches the decrypted key.

### Owner credential vs API-token (agent) credential

Every command that needs the key reads `OWS_PASSPHRASE`, which is **one of two things**:

- The **owner envelope passphrase** — decrypts the wallet's stored mnemonic directly
  (scrypt). Full authority, no policy gate. (Imported wallets use an *empty* passphrase,
  so "owner unlock" is literally `OWS_PASSPHRASE=`.)
- An **API token** (`ows_key_…`) minted by `ows key create` — decrypts the key via HKDF
  and runs **policy enforcement** before releasing it. This is the "agent" path an
  autonomous caller uses.

The token is detected by its `ows_key_` prefix (`key_store::TOKEN_PREFIX`). Both paths
converge on the same signing/balancing code; only the credential-resolution and
policy-gating differ. See [key-create.md](./key-create.md) and [policy-create.md](./policy-create.md).

### The connector pipeline (sign → prove → seal → submit)

On every other chain, `ows sign tx` takes hex-encoded transaction bytes and returns a
signature. On Midnight, the wallet is a **DApp Connector**: it receives a JSON request
describing *what the user wants*, and it constructs, balances, proves, signs, and seals a
complete transaction. The pipeline (detailed in [sign-tx.md](./sign-tx.md)) is:

```
decode_tx_input  →  prepare_signable_tx  →  plan_connector_tx  →  [POLICY SEAM]  →
ConnectorPlan::authorize (build + prove + sign + seal)  →  sealed tx hex
                                                          →  (send-tx only) broadcast
```

The plan is **inert** — it carries no proofs or signatures — so a second, effect-aware
policy pass can veto it *before* any expensive proving happens.
